**Nomva reliability repair plan — September 12, 2026**

Repair the failures that make people distrust the app first, then simplify the underlying flows and prove them on the shipping iPhone build. The code already has useful safeguards, strict AI schemas, batching, local persistence, and test infrastructure. The remaining problems include incomplete data paths, information discarded between layers, and tests that stop before the user sees or saves the result.

This is a plan and source review, not a completed repair. Code reviewed: a6e5846, with a clean tracked working tree before this report. Findings below distinguish source-confirmed behavior, local reproductions, and work requiring a physical device or deployed configuration. No app or server implementation was changed. No personal HealthKit records, Garmin account data, or live AI conversations were inspected.

Jerry confirmed that chat needs improvement in all three areas: understanding/corrections, answer quality, and speed/reliability. The intended weight flow is **Garmin Connect → Apple Health → Nomva, plus Nomva → Apple Health**. Direct Garmin import is an existing compatibility concern, not a prerequisite for that preferred flow.

**2. Repair the AI chat from request to saved result**

Start by extracting mutation execution from ChatView into a testable application service. Keep the existing numeric bounds, candidate guards, strict Responses schemas, database fallbacks, and batch slot validation. Those protections already exist and should remain throughout the migration. Strict schemas guarantee structure, not correct food identity or intent; semantic and persistence checks remain necessary. [OpenAI Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs).

Implement these changes in order:

1. **Return a structured result for every requested item.** Each slot carries a stable ID, parsed description, resolved food and provenance, quantity, date/meal, saved entry IDs, or an explicit unresolved/error reason. Build the final reply from the commit result. Example: “Saved eggs and toast. The yogurt still needs a match.” Keep an Estimated badge and source details wherever an estimate is saved. Retry only unresolved slots. Preserve partial work and unresolved slots after relaunch.
2. **Use entry IDs for edits and deletes.** Give the model a bounded list of current IDs with meal, date/time, brand, portion, and recent operation membership. Require IDs from that list and validate them again immediately before saving. Include a state revision so a stale plan is rejected or reconciled. Ask a short clarification for “delete the coffee” when two entries fit. “Delete both coffees” must explicitly select both IDs. Eliminate fuzzy/name matching as the final authority for destructive actions.
3. **Make local commits idempotent.** Generate a request ID on send and an operation ID for each intended change. Persist operation receipts and data changes together. A retry reuses those IDs; an intentional new message gets new ones. Capture preconditions and undo data for updates/deletes. On relaunch after a save but before acknowledgement, show the saved receipt instead of submitting the meal again. Define atomic groups for dependent actions; unrelated valid food slots may succeed independently.
4. **Fix dates, units, and repeated mentions.** Resolve an explicit date against the user's current timezone and current clock; use the selected day only when no date was stated. Carry that date through parsing, resolution, persistence, and the reply for food, water, and weight. Use one exact pounds/kilograms conversion helper and reject an unresolved unit rather than guessing. Keep repeated food mentions as independent slots or combine their quantities explicitly: the current text-based deduplication can erase a legitimate repeated item. Test DST, midnight, decimal commas, and kg fallback failures.
5. **Consolidate interpretation into one typed turn plan.** Introduce a versioned turn endpoint accepting the current message, selected date, timezone, bounded conversation context, current permitted entity IDs, and unresolved task state. Return ordered actions and clarification needs. This replaces overlapping client heuristics and separate classify/split/extract chains gradually, behind a feature flag. Reuse the food resolver and server batching. The server proposes actions; the client validates and commits local data. Mixed requests such as “log lunch and tell me how much protein is left” should apply the meal first, then answer from the resulting persisted totals.
6. **Maintain useful conversation state.** Persist last committed operation IDs, referenced entries, unresolved slots, and explicit preferences. Supply a compact, bounded history appropriate to the task instead of repeatedly truncating to four messages. Support “make the second one half,” “same breakfast as yesterday,” and answering a portion clarification after interruption. Scope state to a conversation and date; expire stale clarification state and allow a new topic to replace it. Retrieve relevant history on demand rather than uploading the entire record collection.
7. **Improve answers with real application data.** Run totals, averages, changes, remaining calories, and trend calculations in deterministic application code. Distinguish an unlogged day from a measured zero. Provide actual coverage windows and incomplete-data indicators. Use those results to construct concise answers and practical food suggestions with visible assumptions. Keep HealthKit-derived values and summaries on-device under the current privacy promise; local weight questions can be answered with deterministic text. Do not silently send derived Health summaries as a workaround.
8. **Tune models only against representative conversations.** Capture the exact active model and prompt versions first. Compare the present configuration with a small candidate set on complete conversations, portion accuracy, correction accuracy, latency, and cost per successful task. Pin supported model snapshots where available. Select routing from measured results; do not assume that a model upgrade alone repairs missing context or incorrect commits. Keep schema refusal, malformed output, provider outage, and inability to identify a food as distinct outcomes.
9. **Bound latency across the entire turn.** Measure queue wait, authentication, interpretation, lookup, resolution, and save time separately. Cancel queued work promptly. Prioritize interactive chat over opportunistic Garmin/analytics requests and give background work short, cancellable budgets. Use the batch endpoint; invoke single-item compatibility fallback only for an explicit unsupported-route/version response, not every timeout or 429. Respect Retry-After and one total retry/deadline budget. Stop upstream work when a turn is cancelled.
10. **Preserve App Attest replay protection while improving scheduling.** Do not simply remove the gate or release it after signing: the server's monotonic counter checks can reject out-of-order requests. First reduce work and blocking inside the existing protocol. If measured queue wait still misses the target, introduce a short authenticated acceptance step with request-bound operation IDs and scoped result access, then run long work after ordered admission. Add replay, reordering, cancellation, and cross-user access tests before enabling that design.
11. **Show real progress and actionable recovery.** Replace the timer that changes to “Searching foods” for every request with actual stage events. Stream conversational text when appropriate; commit mutations only after a complete validated plan. Preserve a cancelled draft. Display clear connection, permission, rate-limit, and service-unavailable states. Do not count an unsuccessful operation against a future free-message allowance.

**3. Make barcode scanning reliably produce usable food results**

Treat camera recognition, barcode identity, database coverage, and nutrition completeness as separate stages with separate failure reasons. Increasing database size alone cannot fix all four.

1. **Create one barcode value type used everywhere.** Preserve raw code and scanner symbology. Validate supported lengths and check digits; normalize valid UPC-A/EAN-13/GTIN-14 equivalents consistently; expand UPC-E using its symbology. Do not assume every eight-digit code is the same format, strip arbitrary characters into a different identifier, or discard significant identity information. Migrate custom-food barcode aliases without losing the original value or overriding user corrections.
2. **Replace the table scan with indexed exact lookups.** Generate canonical barcode/alias indexes during food database production, then query canonical candidates directly. Rank exact product variants by usable nutrition, brand, serving basis, and freshness. Keep an explicit ambiguous state if records conflict. Validate the migrated index against a frozen set of real codes and compare EXPLAIN QUERY PLAN before and after.
3. **Use a layered lookup.** Check user-owned custom foods, persistent successful lookup cache, and bundled catalog first. On a genuine miss, make an exact product request to Open Food Facts and validate the returned code, product identity, and nutrition. The first implementation can use the public API directly from iOS with a dedicated URLSession, keeping barcode lookup independent of Nomva Cloud's AI queue. Cache useful successes; use short negative caching only for authoritative not-found responses. Never cache a timeout/429 as “food not found.”
4. **Plan for provider capacity rather than assuming unlimited requests.** Current Open Food Facts documentation lists product-read limits of 15 requests per minute per IP, with separate global limits. Use request coalescing and caching, observe Retry-After, and degrade promptly. A centralized proxy would aggregate users behind the same limit; if volume justifies a hosted catalog, refresh it from supported exports. Preserve provider attribution and applicable reuse terms. [Open Food Facts API documentation](https://openfoodfacts.github.io/openfoodfacts-server/api/).
5. **Normalize nutrition conservatively.** Keep per-serving, per-100-g, per-100-ml, and per-container bases distinct. Convert kJ/kcal and salt/sodium explicitly. Do not assume ml equals grams or turn unknown nutrients into zero. A missing serving weight should lead to a supported serving/unit choice, not an invented conversion. Show the food name, brand, package size, serving, calories, and provenance before logging.
6. **Improve recovery after a real miss.** Retain the scanned code and offer Retry, Search by name, Scan nutrition label, and Create food. Reuse the existing label-review flow with the barcode already attached. A confirmed custom food must be recognized on its next equivalent scan, including offline. Never use an LLM to invent an exact branded product from barcode digits.
7. **Fix scanner lifecycle and feedback.** Handle first authorization, denial, restrictions, no camera, interruption, background/foreground, and cancellation explicitly. Configure/start/stop AVCaptureSession on the camera queue; current scan completion and view disappearance stop it on the main thread. Check supported metadata types, use the visible scan region as the actual region of interest, and test focus/torch/orientation and sheet handoff on physical hardware. Reject irrelevant code formats with a clear message.
8. **Measure the full funnel.** Count camera decode success, validation failures, local hit, cached hit, remote hit, incomplete nutrition, timeout, unknown product, and successful save. Operational events should contain no raw barcode or personal food details. Capture actual failing products only through an explicit user-provided diagnostic/example workflow.

**4. Implement dependable weight synchronization through Apple Health**

The supported flow should be visible in settings:

| Direction | Expected behavior |
| --- | --- |
| Garmin Connect → Apple Health | Garmin's app performs this transfer. Nomva helps explain setup and where the latest visible sample stops. |
| Apple Health → Nomva | Import available history, then reconcile new/changed/deleted samples through an app-level coordinator. Retain originating source information. |
| Nomva → Apple Health | Save, edit, and delete Nomva-origin weigh-ins when export is enabled, with persistent pending/error state and retry. |

Garmin's official support guidance says its app must be in the foreground for transfers to Apple Health and describes an initial history window of up to two weeks. Nomva cannot retrieve older Garmin records that never reached HealthKit by repeatedly querying HealthKit. Setup and history messages must explain that distinction. [Garmin sharing guidance](https://support.garmin.com/en-NZ/?faq=lK5FPB9iPF5PXFkIpFlFPA&productID=125677).

There is also a storage boundary to resolve before extending sync. The current model puts imported weights into the active store, which can be CloudKit-backed. Apple's current guideline 5.1.3(ii) prohibits storing personal health information in iCloud. The conservative design for this repair is a protected device store for body-weight data, with HealthKit providing the health-data exchange path. Do not expand the existing CloudKit weight replication without resolving that review requirement. Audit health-derived notes, summaries, archives, and backup eligibility as part of the same boundary. [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research), [current store configuration](/Users/jerrycrews/Documents/Projects/Nomva/Nomva/NomvaApp.swift:158).

Implement the following:

1. **Add an app-level sync coordinator.** Initialize it at application startup; refresh on foreground, explicit Sync Now, and HealthKit change delivery. Serialize reconciliation for the same store, coalesce repeated requests, and pause safely during local/iCloud store switching. Do not require opening the Weight tab.
2. **Use incremental HealthKit queries.** Replace full-history polling with an initial paginated anchored query followed by saved anchors and an observer registered for background delivery. Process added samples and deleted objects; persist the local merge before advancing the anchor. Store cursors per local device/Health store, not in a shared CloudKit record. Handle interrupted imports, permission changes, and cursor reset deliberately. [Apple anchored query documentation](https://developer.apple.com/documentation/healthkit/hkanchoredobjectquery), [deleted objects](https://developer.apple.com/documentation/healthkit/hkdeletedobject).
3. **Represent identity and provenance explicitly.** Keep a stable Nomva entry UUID plus linked provider sample IDs, source bundle identifier/name, measurement timestamp, import timestamp, and revision. Treat a repeated HealthKit UUID as the same sample. Do not automatically merge two different samples from the same source because their values are close. When reconciling older direct-Garmin imports with HealthKit, preserve both identifiers on a confirmed link; leave uncertain matches separate and offer an explicit duplicate-resolution action.
4. **Add a durable export outbox.** Save a Nomva weight mutation and its pending Health operation together. Retry after temporary failure, unlock, permission repair, or relaunch. Export only dirty entries, coalesce repeated edits, retain stable sync identifiers, and increase sync versions only for real mutations. Reconcile an ambiguous acknowledgement before creating another sample. Keep current stored pounds for compatibility during this repair, while centralizing exact unit conversion; a unit-only storage migration is unnecessary.
5. **Specify deletion and editing semantics.** Deleting a Nomva-created entry queues deletion of the corresponding app-owned Health sample and records a tombstone to prevent reimport. Undo must cancel or compensate for that export. Deleting an imported Garmin/third-party sample in Nomva means hiding it locally with a persistent suppression record; Apple permits apps to manage only the Health objects they created. Expose the source app for upstream corrections. A local correction to an imported value must be explicit and preserve the original provenance, rather than silently changing a record that the next import overwrites. [Apple deletion behavior](https://developer.apple.com/documentation/healthkit/hkhealthstore/delete%28_%3Awithcompletion%3A%29-78l1m?changes=_2).
6. **Handle permissions honestly.** Track write authorization separately from whether a read query returned records. Request completion or an empty query cannot establish that read permission was granted. Show “No readable weigh-ins found” and a setup/check action where appropriate; respect limited-history authorization on supported OS versions. Do not remove local history because a query returns nothing. [Apple Health authorization](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data).
7. **Expose useful sync status.** Show last successful read, latest measurement timestamp/source, pending export count, last failed operation, and actual imported date coverage. A saved weight can say “Saved in Nomva; waiting for Apple Health.” Separate that from iCloud status and Garmin activity connectivity. A disabled source stops future operations without erasing existing history.
8. **Make migration preserve data and the storage boundary.** Migrate existing weight records into the protected local weight store, retaining IDs and provenance. Keep Health cursors, suppression records, and export operations out of general CloudKit replication. Preserve existing copies until migration counts and recoverability are verified; handle any legacy cloud cleanup as a separate, reviewed migration. Exercise archive round trips with an explicit health-data policy, iCloud on/off for other app data, restore, two-device HealthKit import, concurrent edits, and app reinstallation. Keep device-specific cursors separate from sample identity. Prevent two devices from generating conflicting export versions or duplicate imports; define one export owner or a tested revision policy before enabling multi-device export.
9. **Guide the exact Garmin chain.** During setup, verify that Garmin Connect is permitted to write Weight in Apple Health and Nomva is permitted to read Weight. Ask the user to complete a Garmin sync with Connect open when Health has no recent Garmin sample. Once a sample is readable in HealthKit, Nomva should show it promptly. Do not label a Garmin account connection as proof that the weight sample arrived.

The direct Garmin route should remain a separately labeled legacy/advanced path while existing users migrate. Remove the one-year promise, return requested versus fetched date coverage and partial failures, and prevent background imports from delaying chat. The cache reload limitation needs explicit treatment. Do not silently add persistent server weight retention to fix it: the current privacy policy promises no retention, and Jerry's preferred flow does not require it. If direct historical import remains a product requirement, implement an approved backfill lifecycle and retention/deletion policy together. Also verify the existing account's protocol entitlement: this code uses OAuth 1.0a, while Garmin's current public developer FAQ describes OAuth 2.0. That mismatch warrants verification, not an unsupported claim that the legacy account is already broken. [Garmin developer FAQ](https://developer.garmin.com/gc-developer-program/program-faq/).
